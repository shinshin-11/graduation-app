## 1. サービス概要

- このサービスはどんなサービスか：
  スーパーの売り場で目の前の食材を検索すると、「美味しい食材の見分け方（目利き）」と「旬・身体へのメリット」を図解カードで一目で把握できる、買い物の判断スピードに特化したビジュアルガイドアプリ。

- 誰の、どんな課題を、どう解決するか：
  環境の変化で買い出し担当になったが目利きに慣れていない人が、混雑した売り場で検索や試行錯誤にかける時間を削り、3秒で納得して最高の食材を選べる体験を提供する。

## 2. このアイデアはどこから生まれたか

### 2-1. きっかけとなった体験・感情

- いつ：
  平日夜や休日に、スーパーの野菜・魚・肉売り場で買い物している時。

- どんな状況で：
  「この時期、どれを選んだら甘い・美味しいのか」「体にどういいのか」が気になり、片手に買い物カゴを持ちながらスマホでGoogle検索やAI（Copilot等）に問いかけた。

- どんな気持ちになったか：
  検索結果には長文のブログ記事やテキストが並び、周りに人が行き交う混雑した売り場で1つ1つ記事を開いて読み比べるのが非常に手間に感じた。また、パートナーに毎回LINEで確認するのも気が引け、「立ち止まらずに図解で答えだけがパッとわかるツールが欲しい」と強く感じた。

### 2-2. なぜそれが「気になった」のか

- 自分の性格・価値観：
  限られた日常の時間の中で無駄な検索・滞留時間を減らし、効率よく納得感のある買い物をしたい（タイムパフォーマンスを重視する）価値観があるため。

- 過去の経験：
  文字量の多い文章サイトよりも、図解やカード形式で直感的に要点だけを把握できるUI/UXを好む性格であるため。

## 3. 課題の整理（表面的になっていないか）

### 3-1. 表に見えている困りごと

- スーパーの売り場で、どれが良い食材か判断するのに検索時間がかかる・迷う。

### 3-2. 本当に解決したい課題は何か

- なぜ？（1回目）：なぜ検索時間がかかると困るのか？
  → 情報が文章としてWeb上に分散しており、売り場でサッと解読しづらいから。

- なぜ？（2回目）：なぜ解読しづらいと困るのか？
  → カゴを持ち、周りに人がいる売り場の環境でスマホを読み込むのはストレスで、買い物の意思決定が遅れるから。

- なぜ？（3回目）：なぜ意思決定が遅れると困るのか？
  → 家族のために失敗なく身体に良い食材を選びたいのに、自信を持った買い物がスムーズにできないから。

- なぜ？(4回目・追加)：なぜ自信が持てないと困るのか？
  → 「家事・買い出しを任された立場として、頼りにならないと思われたくない」という気持ちがあり、食材選びの失敗が、パートナーや家族との信頼関係における小さな自己肯定感の低下につながるから。

→ 本当に解決したい課題：
混雑したスーパーの売り場で、立ち止まることなく「目の前の食材の価値(目利き・旬・効能)」を数秒で直感的に理解し、「任された役割をちゃんとこなせている」という安心感を得ながら、ストレスなく納得して買い物したい。

## 4. 想定ユーザーについて

### 4-1. 想定しているユーザー

- ペルソナ像：
  妻の妊娠・出産や共働き化などのライフイベントにより、急に家族の「買い出し担当」になったが、食材の目利きに慣れていない30代男性。

- 年齢設定：30代前半
  - 理由：結婚や出産などのライフイベントで家事の役割分担が変わり、買い出しの機会が急増する一方で、食材の選び方にまだ慣れていない世代であるため。

- 生活・状況設定：
  頼まれた食材を買うため、混雑したスーパーの売り場で片手に買い物カゴを持ちながら選定している場面。
  - 理由：パートナーに「どれを買えばいい？」と何度もLINEで確認するのも気が引け、一人で素早く正解を選びたいため。

- 環境設定：
  周囲に他の買い物客がおり、素早い移動や判断が求められる環境。
  - 理由：長文記事のスクロールや複数サイトの往復というハードルを、カード型のシンプルな画面設計で解消する。

### 4-2. 自分とユーザーの距離

- 選定：自分自身（およびそのパートナー）
- 理由：買い出しの機会が増える中で「どれを選べば正解なのか分からない」という困りごとや、Google検索のテキスト量に辟易したリアルな体験に基づいているため。

### 4-3. 実際に使われる可能性について(需要・存在確認)

- 最初に使ってくれそうな人：
  買い出しに慣れていない同世代の既婚男性、一人暮らしを始めたばかりの若手社会人。

- どんな場面で思い出すか：
  スーパーで「美味しい見分け方なんだっけ？」「今が旬だっけ？」と食材を目の前にして迷った瞬間。

- 代わりに使っているもの：
  パートナーへのLINE確認、Google検索、Copilotなどの生成AI、既存の食材辞典アプリ。

- 置き換えて使う理由：
  LINEで訊く気兼ねがなくなり、長文テキストや動画と違って「売り場での一瞬の判断（目利き・旬・効能）」に図解で特化しているため。

- 実際にフィードバックをもらった一次情報：
  妻に構想を話したところ、「文字を打つ操作が発生した時点で、結局Google検索と体感が変わらなくなる」「タップだけで完結すること、かつ選択の階層が浅いことが最も重要」という意見をもらった。この反応から、検索窓による入力をメイン導線にするのではなく、タップ操作のみで完結する設計が必須条件であることが確認できた。

### 4-4. ユーザーがサービスを導入して利用するまでのイメージ(導入・継続の流れ)

- どんな場面・困りごとがきっかけで知るか：
  買い出しで選んだ食材が傷んでいた・美味しくなかった経験をし、「次は失敗したくない」と思った時。

- 最初の一歩（登録・導入）：
  アプリを開き、「野菜／魚／肉」などの大分類アイコンをタップ→よく使う食材アイコンをタップ、という最大2階層のタップ操作のみで目的の情報にたどり着ける設計にする（検索窓は補助的な位置づけとし、メイン導線にはしない）。会員登録なしでも即座に閲覧可能にする。

- 利用を続ける理由：
  すべての食材の目利きや時期ごとの見分け方を暗記することは困難であり、季節ごとの旬の入れ替わりから「毎回、今の正解が違う」という前提のもとで確認ツールとして定着する。加えて、アプリ内に「これまで確認した食材」や「今が旬の食材一覧」を残すことで、単なる一問一答の辞書ではなく、自分の買い出し履歴・目利きの成長が見える場所として使い続けたくなる設計にする。

## 5. 既存サービス・競合調査

### 5-1. 似たサービスの調査

- サービス名：
  第一三共『e食材辞典』 / 各種食材辞書アプリ / カメラAI判定アプリ

- URL：
  https://doucore.com/106893/ （第一三共『e食材辞典』の例）

- どんなことができるか：
  食材の選び方、旬、下処理、栄養素、レシピなどがテキスト形式やデータベース形式で網羅的に調べられる。

### 5-2. それでも自分が作りたい理由

- 既存の食材辞典アプリは「百科事典のようにテキストが長々と書かれた構成」になっており、人が行き交うスーパーの売り場でサッと解読するには向いていない。
- 「下処理」や「レシピ」など売り場では不要な情報も多く、本当に知りたい「目利き（選び方）」にたどり着くまでに時間がかかる。
- カメラ撮影で鮮度判定するAIアプリもあるが、混雑する売り場で野菜1つずつにカメラを向けるのは心理的ハードルが高く実用的ではない。

### 5-3. 差別化を「体験価値」で表現する

- 私のアプリの差別化ポイント：
  【買い出しに慣れていない人が混雑したスーパーで】、【文字を読まず・タップだけで】3秒で一番良い食材を見分けられる体験。検索窓に食材名を打ち込む手間すら省き、「よく買う食材」のアイコンをワンタップ、または今の季節の旬食材をあらかじめ先頭に表示することで、Google検索や辞典アプリより体感速度で明確に上回る。

  なお、カメラで鮮度判定するAIアプリとは異なり、本アプリは目の前の「その1個」が傷んでいるかどうかを個体判定するものではない。狙いは、良い食材を見分けるための基準（色・形・重さなど）をユーザー自身が瞬時に頭に入れ、その場で自分の目で正しく選べるようになることであり、ユーザーの「目利き力」そのものを底上げする立ち位置のアプリである。

## 6. このサービスで提供したい価値

### 6-1. ユーザーの変化

- 行動の変化：
  売り場で長文記事を検索したりパートナーにLINEで尋ねたりせず、アプリを2タップするだけで数秒で確実な食材選定ができるようになる。

- 気持ちの変化：
  「これで合っているだろうか…」という不安や気まずさがなくなり、「自分の目で良い食材を選べた」「買い出し担当として頼もしく成長している」という達成感と安心感を得られる。

- 考え方の変化：
  「食材選びは経験豊富な人しかできない難しいもの」から「ポイントさえ押さえれば、自分の目で見て正しく選べるもの」へと意識が変わる。

### 6-2. 価値を一文で表す

- このサービスは【買い出しに慣れていない人】が、【まず売り場で迷わず安心して最高の食材を選べるようになり、使い続けるほどそれが自分の"目利き力の成長"として実感できる】サービス。

## 7. このアプリで実現すること

### MVPで作る機能（【レベル1：迷わず買う】に特化）

- TOP画面（よく使う食材＆大分類アイコン）：
  アプリを開いた瞬間に、代表的な定番食材アイコンが並び、ワンタップで目利き画面へ遷移できる構成。

- カテゴリタップ導線（最大2階層）：
  「野菜 / 魚 / 肉」の大分類アイコンタップ → 代表的な食材アイコン一覧画面の、合計2タップで目的の食材に到達できるUI。

- 図解目利きカード画面（詳細）：
  「見分け方のポイント（視覚的なイラスト＋ワンフレーズ解説）」のみに100%特化したシンプルなビジュアルカード。

- お気に入り/マイ食材ショートカット：
  よく買う食材（キャベツ、サバなど）をトップ付近にピン留めし、次回から1タップで確認できる機能。会員登録は行わず、ブラウザのlocalStorage（端末内保存）にピン留め情報を保持することで、導入ハードルの低さを最優先する。

※管理画面一式を、開発期間内に収められるかは、進捗を見ながら定期的に確認する。もし厳しそうであれば、「管理画面のCRUDのうち、まずは食材の登録・一覧のみをMVPに含め、編集・削除機能は本リリースに回す」といった追加の絞り込みも検討する。

### 本リリースで作る機能（【レベル2：長持ちさせる】＆【ゲーミフィケーション】）

- 【レベル2機能】保存方法・長持ちのコツ画面：
  買ってきた食材を家で長持ちさせるための「正しい保存手順（冷蔵/冷凍/常温のポイント）」を表示する機能。

- 買い出し成長ログ・マイページ（ゲーミフィケーション）：
  - 確認・調達回数のカウント機能（「キャベツ：確認・調達5回」など、利用頻度を数値化）。
  - 食材ごとの「目利き熟練度ランク」（例：確認回数に応じて「ビギナー → ルーキー → マスター」と変化）。
  - 確認した食材の履歴表示により、自分の目利き知識の広がりを可視化。

- 補助的なキーワード検索機能：
  マイナーな食材や一覧から見つけづらい食材用の検索窓。

## 8. このアプリの懸念点とその対策

### 懸念点①

- 何が問題になりそうか：
  食材ごとの「図解ビジュアル」や「目利きデータ」の作成コストが高く、開発が長期化するリスクがある。

- なぜそう思うか：
  多数の食材データを自作しようとすると、プログラミング以外のデータ登録作業に膨大な時間を取られてしまうため。

- そのために考えている対策：
  MVPでは掲載する食材を「スーパーでよく買われる定番野菜・魚の15〜20種類」に徹底的に絞り込む。画像素材は統一感のあるライセンスフリー素材や生成AIを活用して効率的に作成する。

### 懸念点②

- 何が問題になりそうか：
  タップ導線に寄せることで、掲載食材が増えた際に目的の食材が探しにくくなる可能性がある。

- なぜそう思うか：
  検索窓をメインにしない設計のため、アイコンが画面に溢れると目視で探す手間（認知負荷）が発生するため。

- そのために考えている対策：
  MVPでは全ユーザー共通の「定番食材トップ6」を優先表示する形にとどめ、個人ごとの閲覧履歴に基づく出し分けは本リリース以降の課題とする。個人化を行う場合も、会員登録は必須にせず、端末内保存（localStorage）による軽量なパーソナライズにとどめる方針とする。

### 懸念点③

- 何が問題になりそうか：
  「お気に入り」「買い出し成長ログ」など、個人の利用履歴を前提とした機能と、「会員登録なしで使える」という導入ハードルの低さが、設計上両立しにくい。

- なぜそう思うか：
  履歴データを保存するには何らかの形でユーザー（または端末）を識別する必要があるが、本アプリは「忙しい男性がまずログインなしでさっと使えること」を最優先しているため。

- そのために考えている対策：
  MVP・本リリースともに、会員登録を課さずブラウザのlocalStorage（端末内保存）でユーザーごとの履歴・成長ログを保持する設計とする。機種変更等でデータが引き継がれない制約は許容し、将来的に「データを引き継ぎたい」というニーズが強まれば、任意のアカウント連携機能（ログインしなくても使えるが、希望者だけ紐付けられる形）を後から追加検討する。

## 9. 今後の展開・発展の方向性

### 今考えている発展案（ユーザーの成長ステップと連動した拡張）

**・ユーザーの成長に応じた段階的ロードマップ：**

- 【レベル1（MVP）】：目利き（売り場で迷わず最高の食材を見分ける）
- 【レベル2（本リリース）】：保存・長持ち（家での保存手順や長持ちのコツを提示し、買い出しから管理までの成功体験をトータルで高める）
- 【レベル3（将来展開）】：旬・経済価値の提示（買い出しに慣れた段階で、季節ごとの旬の"深さ"や価格傾向など、プラスαの判断材料を解放する）

**・旬の3段階化と価格傾向の掛け合わせ（レベル3の中核案）**

MVPでは「旬かどうか」のみを扱うが、将来的には旬を「入り口／ピーク／終わりかけ」の3段階に詳細化し、それぞれに応じた一言コメントを目利きカードに添える。

- 旬の入り口：これから出荷量が増えていく時期のため、今後さらに値ごろ・味も良くなっていく可能性が高い時期
- 旬のピーク：出回り量・味・価格のバランスが最も良い、いま最も選ぶべき時期
- 旬の終わりかけ：今後は出荷が減っていくため、次第に価格が上がっていく可能性が高い時期

これにより、ユーザーの「今買うべきか、来月まで待つべきか」という買い出しの意思決定に、単なる「旬か否か」の二択より一歩踏み込んだ判断材料を提供できる。

補足として、農林水産省が毎月公表している「野菜の生育状況及び価格見通し」（東京都中央卸売市場の卸売価格を基にした、翌月の平年比の見通し）も参考情報として組み合わせられる。ただし、このデータは月次・定性的な見通しであり、週単位の予測や個別店舗の値札とは連動しないため、表現は「〜の時期は値ごろになりやすい傾向があります」といった傾向ベースの言い回しに統一し、「安くなります」等の断定は避ける。実装上も、既存の「旬」データの拡張（3段階への分割）が中心となり、農水省データの反映は月次の手動更新で対応する想定のため、新たな技術基盤は不要。

**・ゲーミフィケーション要素の強化：**

「春の野菜マスター」「目利きレベル10」などの称号・バッジシステムを導入し、買い出し作業をゲーム感覚で継続・成長できる体験を提供する。

**・UI・体験の工夫：**

- 片手で買い物カゴを持ちながら操作することを前提とした「片手（親指）特化型UI（サムゾーン設計）」の追求。
- システム側で日付（季節）を自動判定し、季節によって同じ食材でも「春キャベツ/冬キャベツ」のように目利きカードの表示内容を自動切り替えする仕組み（旬の3段階化と合わせて発展させる想定）。

## 10. 技術スタック・インフラ構成

### 10-1. 全体方針

- 食材データ（写真・解説・季節情報等）の追加・更新を柔軟に行い、運営側がコードを触ることなく安全・スピーディーに管理できるシステム構成とする。
- ユーザー側は会員登録不要で即座に使える快適性を追求し、端末内保存（localStorage）とバックエンド処理を明確に分離することで、サーバー負荷の低減と高速レスポンスを実現する。

### 10-2. バックエンド・データベース

- 言語・フレームワーク：
  Ruby / Ruby on Rails
  - 選定理由：データの登録・編集・削除（CRUD機能）や管理者認証などのバックオフィス機能を迅速かつ堅牢に構築でき、将来的な機能拡張（お気に入りランキング、検索機能強化など）にも柔軟に対応できるため。

- データベース：
  PostgreSQL(Supabase無料枠)
  - 選定理由：食材マスターデータ、カテゴリ構造、目利きポイントなどのリレーショナル（関連性のある）データを正確かつ高速に管理・検索できる信頼性の高いデータベースであるため。

### 10-3. フロントエンド・閲覧体験（ユーザー側）

- 画面描画・UIレイアウト：
  HTML5 / CSS3 / Tailwind CSS
  - 選定理由：スーパーの売り場でスマートフォンを片手操作するユーザーに対し、視認性が高く押しやすいボタン配置や軽量なUIを効率的に構築・調整できるため。

- クライアント側データ保持（お気に入り・買い出しログ）：
  JavaScript（Web Storage API / localStorage）
  - 選定理由：ユーザー登録やログインの手間を一切なくすため、お気に入り食材や閲覧履歴などのデータはサーバーではなくユーザーのスマートフォン端末内に保存する。これにより個人情報保持のセキュリティリスクを排除しつつ、爆速な画面遷移を実現する。

### 10-4. 管理機能（バックオフィス）

- 管理者認証：
  Rails標準のHTTP Basic認証をAdmin::BaseControllerに実装し、管理画面(/admin配下)全体へのアクセスを制限する。ユーザーテーブルへのrole(権限)カラムの追加や、専用のログイン画面・セッション管理は行わず、最小限の実装に留める。IDとパスワードはソースコードに直接書き込まず、Rails credentials(または環境変数)で管理する。

- 管理画面のCRUD機能：
  新しいgemやフレームワーク(RailsAdmin、ActiveAdmin等)は導入せず、標準的なRailsのCRUD実装パターン(controller/viewでの一覧・新規作成・編集・削除)をそのまま応用して構築する。

- デザイン：
  ユーザー画面側ですでに採用しているTailwind CSSをそのまま管理画面にも適用する。

- 提供機能：
  ブラウザ上の専用画面から、新しい食材の追加登録、目利きイラスト/写真のアップロード、解説文の編集・削除を直感的に実行可能。非エンジニアの運営スタッフでも日々の情報更新や季節の食材追加を安全・タイムリーに行うことができ、運用コストと更新ロスタイムを削減する。

### 10-5. インフラ・運用コスト最適化

- アプリケーションサーバー：
  Render（Web Service）
  - 選定理由：Git（コード管理）と連携した自動デプロイ（CI/CD）に対応し、システムの修繕や新機能のリリースを迅速かつ安全に行えるクラウド環境であるため。

- 応答速度の維持対策（スリープ防止）：
  Google Apps Script（GAS）による定期アクセス
  - 目的・効果：以下の2つの異なる休止の仕組みに対応するため、GASから定期的に自動アクセスを送る。
    - Render(Web Service)側：15分間アクセスがないと発生する約50秒の起動遅延を防ぐため、定期的にアプリのURLへアクセスする。
    - Supabase(無料DB)側：7日間アクセスがないとプロジェクト自体が一時停止する仕様があるため、GASが叩くURLは、DBへの問い合わせを実際に発生させるページ(例:食材データを1件取得して表示するページ)にする。
